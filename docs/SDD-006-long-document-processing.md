# SDD-006：简化为网页全文直传

> 2026-10-19 修订。按用户决定取消旧稿的网页分段 RAG、意图分流和分层总结。旧设计仅保留在 Git 历史，不再作为开发任务。个人知识库原有的向量检索继续保留。

## 现在采用什么方案

读取当前网页已经加载的主要正文，点击开始后，把问题、完整正文和检索到的个人笔记一起交给 Qwen。普通问答和“总结这篇文章”走同一条流程，由模型直接生成回答。

    网页正文读取完成
        ↓
    用户输入问题
        ↓
    固定本次资料范围，按开关搜索个人笔记
        ↓
    完整正文直接交给 Qwen
        ↓
    模型在用户允许联网时按需调用工具，再给出带引用的回答
        ↓
    用户编辑并确认保存笔记

不再为网页建立临时向量索引，不引入问题意图分类器，不添加网页内检索工具，不分段总结后汇总，也不保留自行设定的六万 Token 之类输入预算。

## 前端怎么展示

网页标题、读取状态和问题输入放在同一张卡片。代码里保留网页信息组件和研究组件，用 Vue 插槽组合；界面合并不要求把所有逻辑写进同一个大文件。

不显示正文预览，不需要选中文字，也没有部分正文确认。当前页变化后更新网页信息；已经提交的任务继续使用原快照，回答、引用和保存编辑内容保留。

## 读取和长度规则

删除旧的三万字符截取、提交校验和按钮拦截。正文不在前端或后端悄悄裁掉开头以外的内容。

全文指浏览器已经加载并成功提取的主要正文，不包含尚未加载的章节、隐藏内容或其他未授权网页。它不等于网站全部内容。

保留单篇与每次提交正文合计 8 MiB UTF-8 的传输资源上限，后端 JSON 请求体上限为 50 MiB，以容纳 JSON 转义。这个限制用于控制本地请求与内存，不是声称模型只能处理这么多字。超过时明确提示，不裁剪后继续提交。

不假设模型可以无限接收资料。实际超出服务端上下文容量时显示清楚的失败原因，保留问题和上一份完成回答，不自动改成分段检索。模型容量按实际使用的版本与地域确认，不把 1M 当成所有模型通用能力。

## 模型调用保持简单

复用 QwenClient，继续调用现有聊天和工具接口。保留一个可选配置 QWEN_MAX_OUTPUT_TOKENS，默认 8192，仅控制回答最大长度，不限制正文输入字符数。

调用超时为 120 秒。失败时保留原问题，用户可以重试。记录服务端返回的实际 Token 用量，不引入本地分词器，不把近似估算说成服务端精确用量。网页全文与密钥不写进用量日志。

来源仍从实际提供的网页、个人笔记和联网结果构建，内部编号不展示给用户。正文片段只是悬停核对信息，不代表仅把这一小段提交给模型。

## 能用哪些现成库

- Mozilla Readability：提取文章主要内容，继续使用。
- Turndown：将提取的 HTML 转成保留标题、列表和代码块的 Markdown，替换手写节点转文本逻辑。
- turndown-plugin-gfm：转换表格。
- markdown-it 与 DOMPurify：继续负责回答排版和安全清理。

只保留浏览器权限、页面核对、任务快照与来源关联等业务代码，不引入通用 Agent 编排框架。个人知识库 RAG 使用已有 PostgreSQL、pgvector 与向量服务，不受本次简化影响。

## 怎样验收

1. 超过三万字符的普通技术文章能读完并提交，文章末尾确实进入模型请求。
2. 网页信息和问题在同一张卡片，没有正文预览和选区确认。
3. 生成中切页不会取消原任务，回答和保存来源仍是原网页。
4. 标题、代码缩进、表格能通过库转换保留，原页面不被修改。
5. 真实容量超限、读取失败、服务失败有提示；没有悄悄丢弃正文，也没有虚构全文处理进度。
6. 原有个人知识库检索、引用预览和确认保存继续可用。

## 取舍

当前以实现完整闭环和可维护性为先。全文直传的成本与等待时间可能随内容增长，但目前无需为尚未遇到的极端长文搭建三条处理流水线。只有实际使用出现明确问题，再依据记录决定是否重新引入更复杂的方案。

简历应如实写成“基于网页全文、个人知识库检索和受约束工具调用的阅读助手”，不再声称实现长文分层总结或网页分段检索。
