# SDD-006：长文章怎样阅读、检索和总结

> 2026-10-19 设计稿，尚未实现。本轮只写文档，不修改运行代码。当前代码仍以 30,000 字符拦截长文；本文确定替代方案。网页读取见 SDD-001，任务状态见 SDD-002，资料范围见 SDD-005。

## 1. 要解决什么问题

用户正在读技术文章，应该能够直接提问，不需要选中文字、展开正文预览，也不需要自己决定“全文模式”或“RAG 模式”。

现在“三万字符以上就不能回答”的规则只是临时限制，没有充分利用模型的上下文，也无法处理真正的长文章。新的目标是根据可用 Token 预算和问题类型选择做法。

这里说的全文，是浏览器已经加载、成功提取的主要正文。网页尚未加载的章节、隐藏内容、跨域 iframe 等仍不属于已读取范围。模型看过资料也不代表每条结论都准确。

## 2. 三种处理方式

| 条件 | 怎么做 | 主要取舍 |
| --- | --- | --- |
| 资料放得进可用上下文 | 完整正文直接交给 Qwen | 简单、保留上下文；内容越长，成本和等待通常越高 |
| 资料放不下，用户问具体问题 | 将全文分段，在限定资料内检索，再用相关原文回答 | 减少输入；可能漏召回，需要补充相邻段落或再次搜索 |
| 资料放不下，用户要整体总结 | 每一部分先整理，再分层合并 | 覆盖每个部分；调用更多，摘要可能损失细节 |

“全文作为资料范围”不要求每次都把全文塞进一次模型请求。重要的是全文都有机会被处理，而不是固定只保留文章开头。具体问题的检索不能冒充已经逐段阅读全文。

## 3. 用户会怎样使用

打开网页 → 输入问题 → 系统自动选择处理方式 → 展示真实进度 → 返回带原文引用的回答。

例如，同一篇很长的 TypeScript 教程：

- 问“作者怎样解释泛型约束”：在整篇教程中查找相关段落。
- 问“总结这篇教程的知识结构”：处理所有章节后汇总。
- 问“先总结，再详细解释泛型”：先形成整体小结，再检索泛型原文补充解释。

界面不增加正文预览或部分正文确认。只需简单说明“结合全文回答”“正在查找相关章节”或“正在整理第 2/6 部分”。这些状态必须来自实际执行，不能先播放一套固定步骤。

## 4. 先解决预算，而不是换一个字符上限

Token 是模型处理文字的单位，不等于汉字数或英文单词数。同样字符长度的中文、英文和代码，Token 数可能不同。

后端维护当前模型的配置：模型 ID、上下文上限、最大输入、计划输出长度，以及本任务的成本与调用预算。qwen-plus 这类名称可能对应服务端更新，实施时核对北京地域当前实际模型能力，不在文档中编造固定容量。

可用资料预算需要同时满足：

    模型最大输入限制
    上下文上限 - 预留回答 Token
    项目给这次任务设置的输入预算

再从中扣除系统提示、问题、消息封装、工具定义、笔记、工具结果和安全余量，剩下的才是网页资料预算。每次调用模型前重新检查，不能只在任务开始时算一次。

优先使用与实际 Qwen 模型匹配的分词器或官方 Token 计算能力。估算必须标明为估算，并与真实调用返回的 usage 校准；不使用“一个汉字等于一个 Token”这样的固定换算冒充精确值。QwenClient 后续需要返回 usage，并设置输出上限。

预算不够就切换策略，不把正文无提示地截掉。网络请求大小和临时缓存仍需独立的可配置上限；它们是传输与资源限制，不是模型只能处理多少字。接入时前后端一起调整现有 256kb 请求体限制和提取函数的截取逻辑，不能只删除提交按钮上的限制。

## 5. 谁决定采用哪种方式

分两步：

1. **程序判断是否放得下。** 长度、数量、权限、可用模型能力和调用次数是明确规则，不交给模型猜。
2. **放不下时判断问题意图。** 明确的“总结全文”等入口可以直接使用整体总结；普通输入由 Qwen 返回固定结构，类型仅为 focused_question、whole_document 或 mixed。

意图判断只提供问题、标题和有限目录，不先把超长全文塞进去。输出必须校验；判断失败或意图不清时采用覆盖整篇的处理，代价是更慢，而不是静默只搜几个片段。模型返回的“原因”只用于简短解释，不展示内部推理。

这属于固定流程与有限自主决策结合的研究助手。长度分流本身是工作流；Qwen 按问题选择检索词、在允许时补查资料，才是自主工具使用的一部分。不能因为加了几个 if 或用了 RAG 就声称实现了完全自主的 Agent。

## 6. 长文具体问答：在全文中检索

### 建立临时段落索引

按标题、自然段和代码块切分，尽量不从句子或代码中间切开。超长代码块必须拆时保留语言、章节和行范围，并遵守向量模型自己的单次输入限制。

每段保留：任务资料 ID、文档版本、段落 ID、章节路径、原文起止位置、正文、标题和网址。少量重叠或相邻段落扩展用于保留上下文，大小通过样例验证，不把某个固定段长说成最佳值。

所有段落进入索引；不是先截取三万字符再切段。索引未建完时不能声称可搜索全文。临时网页正文与向量放在后端有界会话缓存中，设置过期和清理；第一版可在内存完成，不引入新的向量数据库或 Redis，也不自动写入个人笔记表。

### 回答问题

1. 问题生成向量，搜索当前选定网页的段落；段落向量复用现有 EmbeddingService，不拼接整篇生成一个向量。
2. 同时保留术语、错误码、函数名等关键词匹配。关键词匹配和向量结果合并去重，再用现有相关性判断思路筛选。
3. 加入命中段落的标题和必要相邻内容，在预算内把原文交给 Qwen。
4. 证据不足时，允许一次有上限的改写检索或扩展章节；仍不足就说明文章中没有找到依据，不无限循环。

例如搜索 TS2322 时，不能只找到“TypeScript 类型错误”的泛泛段落，还要关注原文是否确实出现这个错误码。第一步可用简单术语匹配，是否引入 BM25 取决于实际样例效果，不同时堆叠多个检索框架。

后续可将限定文档内搜索开放为 search_page_content 工具，参数只允许选择本次资料 ID 和检索词，不接受任意网址。现有 search_knowledge_base 搜索长期笔记，职责不同；实现时复用分段与检索代码，不复制两套流程。第一阶段先固定检索，再在真实需求下开放给模型调用。

## 7. 长文整体总结：每一部分都处理

具体问题检索容易遗漏其他主题，所以“总结全文”不能只取最相关的前三段。

    全部正文按章节分组
        ↓
    每组生成小结、关键事实与对应原文位置
        ↓
    合并重复观点，保留章节差异与前后条件
        ↓
    若中间小结仍超过预算，继续分组合并
        ↓
    形成最终总结，并关联真实原文引用

这种做法叫分层总结或 Map-Reduce 总结。所有正文分组都应成功处理，才能显示“全文整理完成”。可以从最多两个分组并发起步，再根据限流与等待情况调整；这是可配置初值，不是性能结论。

某一组失败时可有限重试，其他已成功小结可以在任务内复用。仍有失败则明确显示未完成部分，不把其余小结当成完整总结。若预计调用次数或总 Token 超出项目预算，先给出清楚的限制说明，不偷偷跳过章节或无限追加调用。

中间小结是模型生成内容，不能冒充原文。小结保留原文位置及可核对片段，最终引用以真实正文为依据；引用片段需要能在对应版本原文中找到。整体小结和精选原文也要一起计入最终调用预算，超限时继续分层或减少重复材料，不能随意丢掉某个章节的结果。

这种方式让每个部分都被处理，但仍然可能遗漏细节，因此不承诺“全文所有信息毫无损失”。用户追问细节时回到原文段落检索。

## 8. 来源、任务与会话

每次任务固定正文版本。用户切到其他网页后，旧任务仍使用原正文；网页重新读取得到新版本，不能拿旧索引回答新正文的问题。

缓存按本地会话与正文版本隔离，版本至少反映网址、读取快照与内容变化；不得只按 URL 缓存。缓存过期可以用仍持有的原快照重建，不自动改用新页面。浏览器重启、后端重启和关闭侧栏后的恢复边界沿用 SDD-002，不增加后台永久任务。

回答的 sources 扩展为可对应到具体原文段落：文档 ID、段落 ID、章节、网址、片段和原文位置。来源编号仍只在内部使用，界面展示自然引用文字，悬停显示标题、章节和原文。需要扩展现有引用解析器，使同一网页的多段来源也能正确对应；不能只给每段都显示文章开头 1,200 字符。

响应的处理信息应区分：

- direct：完整正文直接进入回答请求。
- retrieval：以全文为检索范围，回答使用命中的段落。
- hierarchical_summary：全部分组处理后形成总结。

“正文提取完整”与“模型每次看过全部原文”是两件事。前端可用通俗提示说明处理方式，不把检索结果标成逐段阅读全文。

普通任务不自动写入个人知识库。用户编辑确认保存时，沿用当前保存接口；正文引用转换为具名链接，内部段落 ID 不进入用户笔记。临时索引过期后，已完成回答仍保留引用片段和网页链接；第一版不保证网页跳转后精确定位到原句。

## 9. 进度、取消与失败

真实事件包括：准备资料、建立索引进度、检索章节、整理分组进度、合并小结、生成回答、完成或失败。进度属于哪个任务由 runId 区分，不随当前浏览页面变化。

点击停止后取消排队分组和进行中的模型请求，不再启动后续步骤。控制并发数、超时、最大重试和总调用预算；失败保留问题与上一份成功回答。整篇总结与检索过程都不能因切页被误中断。

需要把 AbortSignal 从研究请求传到 QwenClient、向量调用和各处理步骤。流式进度沿用 SDD-002 的事件协议，不另建一套长文状态协议。第一阶段尚未接通实时事件时，只显示“正在处理文章”，不展示虚构的分组进度。

记录模式、分组数、实际调用数、Token 用量（或明确标注估算）、耗时和失败原因，供本地排查；不默认把网页全文写入日志。不要求新增一套监控平台。

## 11. 一步步实现

| 步骤 | 工作 | 完成后怎样验证 |
| --- | --- | --- |
| 1 | 核对模型配置、建立预算计算；前后端同步取消三万字符拦截 | 超过三万字符但预算内的文章可直接回答，末尾内容确实传入模型；超预算走待处理提示而非静默截取 |
| 2 | 章节切分、临时缓存和限定网页的段落检索 | 答案在开头、中间、结尾均能召回，技术标识能命中；无关问题明确说没依据 |
| 3 | 问题意图判断、分层总结及失败处理 | 所有分组都处理；遗漏或失败分组不能伪装成完整总结 |
| 4 | 接入来源段落、真实进度、取消和重试 | 悬停看到实际引用段，切页不中断、停止后不继续调用、旧事件不串任务 |
| 5 | 结合 @ 多资料与个人知识库范围 | 检索不越出选定网页；临时网页不污染长期笔记；关闭范围后对应工具不执行 |

步骤 1 不代表已经支持任意长度。步骤 2 的具体问题检索与步骤 3 的整篇总结都完成后，才对外宣称支持长文问答与总结。@ 和流式分别复用 SDD-005、SDD-002，不再建平行实现。

## 12. 怎样证明效果和面试价值

固定几份自己可以核对的样例，不用只看“模型说得像不像”：

- 普通文章与超过旧上限的文章，答案分别位于开头、中间、结尾。
- 包含多个主题、相似术语、错误码和代码段的文章。
- 整篇总结需要覆盖各章节；对比只取前几段会遗漏哪些主题。
- 原文没有答案、某组超时、用户停止、切换标签页、同 URL 正文更新。

记录回答是否有原文支持、总结章节覆盖、耗时、调用次数和实际 Token；没有测过就不写“召回率提高多少”“延迟降低多少”。

对全栈偏前端岗位，这个设计有价值，尤其在于：

1. 把同一个“提问”交互下的不同处理过程组织清楚，展示真实进度。
2. 处理取消、重试、切页、迟到事件和引用预览，让异步任务不串状态。
3. 能说明为什么短文直传、具体问题检索、全文总结分层，以及各自会漏掉什么。
4. 让模型的工具使用受资料范围和预算约束，而不是仅增加工具数量。

完成并验证后，可以说“实现了结合上下文预算、文档检索与分层总结的网页研究助手”。现在仍是设计，简历不能写成已经落地或经过性能验证。长文分流本身不是完全自主 Agent；应如实介绍为工作流与模型工具调用结合。

## 13. 参考了哪些公开方案

- [Recall MCP 文档](https://docs.recall.it/developer/mcp)：公开提供限定文档搜索、分块内容与按问题读取章节的接口；不据此推断其全部内部实现。
- [Readwise Ghostreader 参考](https://docs.readwise.io/reader/guides/ghostreader/reference#document-content)：展示按 Token 长度选择全文或重要句段的做法，不等于所有聊天都采用同一流程。
- [Google 长上下文说明](https://ai.google.dev/gemini-api/docs/long-context)：长上下文的能力、成本、等待与局限。
- [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)：分块检索、关键词与向量结合，以及段落缺少上下文的问题。
- [LangChain 官方总结实现](https://github.com/langchain-ai/langchain/blob/master/libs/langchain/langchain_classic/chains/summarize/chain.py)：参考分段总结再合并的思路，不表示需要引入该框架。

以上用于说明公开能力与通用方法。本项目的路由、缓存、交互和实施顺序是自己的设计，尚无测试结果。
